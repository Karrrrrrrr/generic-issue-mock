# Generic Mock Engineering Rules

## Model Ownership

- This repository simulates third-party channels for downstream systems. In this repository, a channel is the service being simulated; never carry downstream names such as `ThirdPartyID` into a generic model.
- Generic models use an auto-incrementing `int64` primary key `ID` for relations and transactions. A channel service derives every external resource ID from that key with its channel formatter; do not persist `display_id` or add another resource token.
- The channel formatter follows the downstream DTO field type. For a downstream string ID, format the internal `int64` as its decimal string and parse it back with validation. For a downstream numeric ID, pass the `int64` value. Only when the downstream contract requires another format, such as UUID, encode the ID into that required format and implement the inverse parser. Do not add a prefix, offset, hash, or other encoding merely to avoid decimal representation.
- A channel service parses every incoming mock-owned resource ID with its channel ID conversion helpers in `channel/<channel>/pkg/idconv`, exposed as public functions with directional `To...` / `From...` names before invoking a usecase that accepts an internal `ID`. The formatter and parser must be reversible and validate the downstream-required format; responses derive IDs from the relevant model or relation ID at the service boundary.

### Implemented Channel ID Formats

| Channel | OpenAPI and UI resource ID format | Webhook resource ID format | Source of truth |
| --- | --- | --- | --- |
| `slash` | UUID string. Encode the `int64` into the last 8 bytes of a canonical UUID; parse only that canonical form. | No implemented mock-owned webhook ID DTO. Use the same UUID rule when one is added. | `channel/slash/pkg/idconv/id.go` and Slash SDK DTOs. |
| `photonpay` | Decimal string: `strconv.FormatInt(ID, 10)` and `strconv.ParseInt`. | Decimal string for `ds-event` resource IDs such as `cardId` and `transactionId`. | `channel/photonpay/pkg/idconv/id.go` and `pkg/dealer/photonpay` DTOs. |
| `paynda` | Decimal string: `strconv.FormatInt(ID, 10)` and `strconv.ParseInt`. | Numeric `int64` for `xm-event` fields whose Marxo protobuf declares `int64`, including `merchantId`, `balanceAccountId`, `cardholderId`, and `cardId`. String webhook IDs retain decimal-string formatting. | `channel/paynda/pkg/idconv/id.go`, Marxo `notify.proto`, and `pkg/dealer/payndapay` DTOs. |
| `pingpong` | Canonical positive decimal strings through `ToString` / `FromString`; caller idempotency keys are opaque. | Unconfirmed; no webhook DTO or delivery implemented. | `channel/pingpong/pkg/idconv/id.go` and supplied `sdk/pingpong` DTOs; production consumers still pending. |

When a downstream DTO has mixed ID field types, apply the row's webhook rule per field. Do not infer a UUID requirement merely because an SDK uses Go `string`.
- Generic models are shared by every channel. Add a field only when a current channel implementation needs it and it represents a channel-neutral concept.
- Channel-neutral field access and nil-safe defaults belong on the owning model. Implement `(*Account).GetName() string` in `model` and call `item.Account.GetName()` rather than defining service helpers such as `getAccountName`. Keep model accessors pure: no repository access, channel-specific behavior or business-flow orchestration. This does not permit sharing UI/OpenAPI business implementations.
- `Account` is the channel account domain, not a `VirtualAccount` and not a webhook configuration. Keep `Account.Channel`: an account is scoped to the channel that owns it. Every persisted business table other than `Account` and channel-level `CardProduct` must carry both `AccountID` and `Channel`; `AccountID` references `Account.ID` and the row `Channel` must equal its account's `Channel`.
- Account-owned repositories must scope every `Exist`, `Find`, `List`, `Save`, and `Delete` operation by both `AccountID` and `Channel`. A child aggregate inherits that pair from its owning resource in the same transaction. Do not derive the account from an unrelated current/default account, and do not encode either value into a channel external resource ID.
- UI simulation ownership resolution is the explicit exception to supplying account scope: callers send a card ID for authorization/independent refund, or an authorization ID for clearing/reversal/linked refund. Do not require redundant `account_id` or a card ID already determined by the authorization. Dedicated simulation `ExistForSimulation` / `FindForSimulation` operations use the resource primary key and mandatory channel to resolve ownership; all later locks, wallet updates and stage queries still use the derived account/channel pair. Existing transaction-based UI actions resolve their original transaction by ID and channel before invoking the simulator. OpenAPI and non-simulation account-specific mutations retain explicit account selectors.
- Except for the UI simulation ownership lookup described above, account scope is an explicit business input. Channel service code parses its protocol account selector with the channel ID conversion helpers, then puts the internal value in the usecase/repository request struct as `AccountID`; do not put an account ID in `context.Context`, use a middleware-derived account scope, or parse then discard the value. A repository request that identifies an account-owned resource contains both `AccountID` and the resource ID. Its query always includes `channel`, `id`, and `account_id`; list requests include `channel` and add `account_id` when the caller selected an account. UI administration may omit the optional list filter to view all accounts, but create and account-specific mutations must carry a non-zero `AccountID`.
- Every uniqueness rule for account-owned data includes `account_id` and `channel` in addition to its natural key. `Account` itself has no `AccountID`; its `ID` is the domain key and `Channel` remains its channel scope.
- The browser UI is a global administration console with flat cross-account lists, not an account-switched workspace. Do not introduce a global account selector or inject account scope through a shared request interceptor. Account-specific mutations carry the owning account from the operated resource row; creation forms for supported UI resources explicitly specify ownership. Account management remains separate from `VirtualAccount` management. The UI does not create cardholders or issue cards; those operations belong to OpenAPI.
- Every implemented channel must resolve an account before accessing account-owned OpenAPI resources. Paynda resolves the decimal `balanceAccountId` path/body field; PhotonPay resolves decimal `app_id` during `oauth2/token/accessToken` and receives the resulting token in `X-PD-TOKEN` on subsequent requests; Slash resolves its UUID-formatted account ID from the Marxo SDK's `X-API-Key` header. Each service uses a local helper to parse that selector and explicitly passes `AccountID` to its usecase request. These are channel-specific account selectors, not interchangeable authentication rules.
- PhotonPay has no OpenAPI virtual-account selector. Creating a PhotonPay `Account` must create one default `VirtualAccount` and its wallet in the same transaction. UI virtual-account management remains available for additional accounts and funding operations. PhotonPay OpenAPI flows that require a shared card wallet resolve the earliest `VirtualAccount` for the selected account (`ID ASC`), then set `Card.VirtualAccountID` and `Card.WalletID`; they must not expose or infer a PhotonPay-specific virtual-account request parameter.
- `AuthorizationConfig` is the account-scoped configuration for channels with synchronous authorization callbacks. It is separate from `WebhookConfig`, which subscribes asynchronous events. Its uniqueness is `(account_id, channel)` and it is managed through channel UI services; do not expose an OpenAPI configuration endpoint unless Marxo has an actual call site. A failed synchronous authorization callback rejects the simulated transaction; do not persist a fallback behavior. PingPong is explicitly asynchronous and must not use this configuration or callback flow: its webhook reports a local authorization decision, not an approval request.
- A card product configures one or more card BIN candidates in `CardProduct.Prefix`, a string separated by ASCII commas. Only the `pingpong` channel accepts multiple prefixes; all other channels require a single prefix. Every candidate must be non-empty numeric text; trim surrounding whitespace and reject invalid candidates rather than discarding them. `pkg/cardnumber.Generate` validates the full list and sequence capacity before randomly selecting a candidate. Every new card stores both `CardProductID` and only that selected prefix in `CardBin`, and its `CardNumber` starts with the same prefix. Never copy the comma-separated list into a card BIN. Keep `NextCardNumber` shared across all prefixes and accounts of the product, under the existing transaction and product lock; preserve existing single-prefix products and issued cards.
- Card wallet semantics are explicit: `single` has no VA and owns a card wallet; `share` belongs to a VA and reuses its wallet; `virtual_account_single` belongs to a VA but owns a separate card wallet. PingPong OpenAPI calls a `VirtualAccount` a budget group; internally, its virtual-account-linked ordinary card uses `virtual_account_single`, and the virtual account is a funding source, not the spending wallet. Never infer sharing merely from `VirtualAccountID` or a preloaded VA. `Card.WalletID` is authoritative for displayed balance and simulated spending. For the third type, top-ups debit the linked VA wallet and credit the card wallet; withdrawals return to that same VA, with normal positive amount, scope, currency and balance checks. They must not bypass the VA by transferring directly to/from the root account.
- `pkg/cardwallet.Prepare` is the shared pure wallet-assignment helper used from biz: validate account/channel/currency and the referenced VA wallet, return a new card wallet for either independent type or the existing VA wallet for `share`, and retain the VA ID for the third type. Persist a newly allocated wallet and its card in the same transaction. `pkg/cardwallet.FundingWalletID` resolves the funding wallet from the owning relations; missing/invalid relations must fail, not fall back to another account or VA. Lock both transfer wallets by ID order and verify currency/ownership in the channel usecase. Existing channels must not gain new protocol card types without their own confirmed contract.
- Do not add a field merely because it exists in a downstream SDK request or response. Keep such unused fields in the channel service DTO with an `Invalid:` comment and ignore them.
- Before changing a generic model, search the downstream implementation for actual request construction and response consumption. Do not infer persistence fields from third-party SDK type definitions alone.

## Backend Structure

- `pingpong` is partially implemented at HTTP/UI level: 12 core SDK methods, six independent management views and local authorization accounting. Account reporting, card/account transaction reporting and 3DS return explicit 501; `update_remark` is unsupported. Configure `PINGPONG_APP_ACCOUNTS` explicitly as application ID -> decimal account-ID strings; never infer this mapping. Seed one PingPong demo account, virtual account, channel product, cardholder and linked `virtual_account_single` card; seed data does not configure an app mapping or enable webhook delivery. Current mock products/virtual accounts use USD, and virtual-account top-up transfers from the root account. These are documented mock conventions, not verified production contracts. Follow `docs/channels/pingpong.md`; production Marxo call sites and webhook contracts remain missing. Do not fabricate webhook payloads, successful delivery or synchronous callbacks: UI reports `contract_pending` until real asynchronous delivery is implemented.
- `payful` is deprecated and no longer scheduled for implementation. `docs/channels/payful.md` is archived research, not an implementation requirement; do not add Payful APIs, UI, seed data or persistence fields for it.

- Use Gin with Kratos-style layering: `channel/<channel>/service`, `biz`, `data`, and `http`.
- Service methods use `Fn(context.Context, *Request) (*Response, error)`. They bind or convert channel DTOs only; business behavior belongs in `biz`.
- A service response is the channel DTO itself, never a protocol envelope such as `Response[T]`. The channel HTTP adapter wraps successful DTOs in its API envelope. Service translates Kratos business errors to channel-specific error reasons.
- `biz` owns repository interfaces and normally injects repositories, not other usecases. Channel simulation usecases explicitly inject the shared `CardTransactionSimulator`, which composes the shared `BalanceChanger` wallet primitive. This is the approved exception for authorization, clearing (including refund/reversal), accounting and simulation idempotency; channel UI/OpenAPI usecases still must not call each other. Keep each entry point's protocol validation, error conversion and notification adapter independent.
- UI and OpenAPI business implementations are intentionally independent. Apart from the explicitly approved shared simulator, only repository implementations are reusable between them; identical current behavior is not a reason to share a business flow. Each concrete usecase declares and injects its own required dependencies and owns its requests and validation. Non-simulation flows retain independently implemented state changes, transactions and private helpers. Never place behavior on `dependencies`, inherit it from a common base usecase, or route both entry points through another shared business helper. This separation preserves room for different operation logs and future rules.
- Organize biz files by business domain, not just by layer. Do not collect an entire channel's repositories in `repository.go` or its business methods in `usecase.go`. For example, account contracts and their operation-specific requests belong in `account_repository.go`, UI account behavior in `account_ui.go`, and OpenAPI account behavior in `account_openapi.go`. Repository parameter structs are declared at the top of the same repository file, after package/imports and before interfaces. Keep UI/OpenAPI behavior separate; small constructor/composition files may wire dependencies but do not contain business methods. Group definitions by their owning business rather than creating one file per parameter type.
- `data` implements repositories. A repository method performs exactly one database operation.
- Define repository request structs in biz separately from service and usecase requests. Each repository operation that accepts a request has its own resource-and-operation-specific type, such as `FindWalletRequest` or `ListCardsRequest`. Do not share ambiguous catch-all requests such as `ManagementScope`, `ResourceRequest`, or a channel-wide `ListRequest` across operations, even when their fields currently match. Reusable field groups may be embedded in each operation's own request; do not replace dedicated request types with aliases. Separate types do not require separate files or new repositories.
- Use `samber/do` for dependency injection. Register constructors directly as providers and resolve dependencies inside those constructors; do not construct dependency graphs manually in `main`.
- Keep each channel in its own package and expose all routes under `/<channel>/...`.
- Simulation endpoints belong only to the UI management surface. Do not register OpenAPI simulation routes or inject `CardTransactionSimulator` into OpenAPI usecases. SDK transaction-query tests prepare data through UI authorization/clearing/refund/reversal endpoints; SDK implementations remain unchanged.
- Within each channel router, use only two Gin `RouterGroup` groups: OpenAPI and UI. Do not add business-module subgroups. Preserve the existing protocol paths: UI uses `/ui`, Paynda OpenAPI uses `/openapi`, and Slash/PhotonPay OpenAPI uses an empty group prefix. Retain parameter names, HTTP methods, and handler bindings.
- For Slash, browser management flows use `/slash/ui/...`; Marxo integrations use the Slash OpenAPI paths directly below `/slash/...`. UI handlers must not substitute for, or redefine, the OpenAPI contract.
- Frontend business views belong to their own `frontend/src/channel/<channel>` directory. Channel routes must reference their own views; do not import another channel's business component or turn it into a shared view by switching the channel from the URL or injecting another channel's API.
- `WalletTransfer` is an account/channel-scoped immutable successful funding record with request idempotency and both wallets' before/after snapshots. Its optional card relation stays nil for virtual-account transfers; never fabricate a card or derive history from mutable last-operation fields.
- Do not add a standalone funds-management page. The account page adjusts its wallet balance directly without a funding source. Virtual-account and independent-card pages recharge from, and withdraw to, their owning account wallet; virtual-account-linked independent cards instead transfer with their linked VA wallet; transfers must preserve the combined balance, validate account and currency, and reject insufficient funds.
- Paynda has no virtual accounts. Do not add virtual-account pages, UI endpoints, repositories, or shared virtual-account card funding to Paynda. Its funding operations involve only account wallets and independent card wallets.

## HTTP, Types, and Persistence

- Simulation amounts are strictly positive. All channels use the same accounting rules: `CardTransactionSimulator` owns the operation flow and calls the shared `BalanceChanger` to apply wallet mutations; do not introduce a channel-selectable accounting strategy or treat inconsistent old implementations as channel-specific behavior. Wallet `Available` (database column `available`) is available balance, `PendingOut` is frozen balance, and total balance is `Available + PendingOut`; availability checks and responses use `Available` directly, not `Available - PendingOut`. Operation and transaction amounts stay named `Amount`; wallet delta requests use `AvailableDelta`. Authorization checks `Card.WalletID`'s available balance and transfers the authorization amount from `Available` to `PendingOut`; insufficient balance rejects authorization, and successful authorization changes neither total balance nor `Out`. Clearing/reversal hold release is `min(operation amount, max(authorization remaining amount, 0))`. Clearing subtracts that release from `PendingOut`, updates `Available += released hold - clearing amount`, and increases `Out` by the full clearing amount; already frozen funds must not be debited twice. Refunds directly increase `Available` and `In` without changing `PendingOut` or authorization remaining amounts. Reversal transfers the released hold from `PendingOut` back to `Available`, without changing total balance, `In` or `Out`. Simulated clearing may exceed wallet balances and authorization amounts for all channels. Negative wallet balances and negative remaining authorization amounts must not disable or reject subsequent clearing. Return signed remaining amounts without clamping. Preserve normal insufficient-funds checks for account/card/virtual-account wallet transfers.
- `BalanceChanger` exposes generic delta changes, simple signed changes, and Try/Confirm/Cancel wallet operations through an interface with a private implementation and a compile-time assertion. Use model int64 IDs (`AccountID`, `WalletID`) plus `Channel` and `Currency`; reuse `model.Wallet` instead of copying another project's merchant/account/balance DTO. Confirm takes an explicit non-negative released amount no greater than the debit amount, including zero for continued over-clearing. Currency and scope are validated on the locked wallet, and frozen balance and cumulative `In`/`Out` cannot become negative. `CheckAvailable` controls negative available balances, not the frozen/counter checks. The shared `Transaction` interface exposes `IsInTx(ctx)` so the component joins an existing context transaction or starts one itself, without an `IsInTx` request flag or a GORM handle in biz. Only the outer simulator commits its complete business flow before notifying; the wallet primitive has no notification, automatic idempotency, DTM integration or TCC state table.
- PingPong UI authorization is a local decision followed by an asynchronous webhook and uses the same accounting rules as every other channel. In the scoped transaction, lock the card's own `Card.WalletID` and check available balance against the positive requested amount; do not use VA or root-account funds as a fallback. Insufficient balance rejects the authorization and sends no authorization-success notification. Commit the local authorization and its consistent accounting/delivery state before network delivery. Never wait for downstream approval, call a synchronous authorization endpoint or require `AuthorizationConfig`. Delivery ACKs, timeouts and failures affect webhook delivery status only, not the committed authorization result; retry/replay must not repeat authorization accounting. The user has confirmed this flow, while payload/event/signature/ACK details remain unconfirmed. Clearing retains the common over-clearing rules.
- Clearing and reversal require an existing authorization with non-zero `AuthorizationID`, matching account, channel, and card. Refunds may be initiated independently with persisted `AuthorizationID = 0`, or linked to an existing authorization; a prior clearing transaction is not required. An optional authorization request field is a pointer (omitted/null means independent); supplied IDs are parsed with channel helpers and validated. Authorization and clearing are not defined as opposite accounting directions.
- Return `account_name` and `account_id` together in existing account-associated UI endpoint responses. Resolve the current account name on the backend without persisting duplicate names in business rows. Frontends must not fetch accounts separately just to render names; fetching options for an account-selection form is allowed.
- For the optional refund authorization specifically, an explicitly supplied channel-formatted zero ID also means an independent refund (zero is a valid domain value here, not an omission sentinel). Other supplied IDs must identify an existing authorization. Clearing and reversal do not accept zero authorization IDs.

- Define typed request and response structs with `json`, `form`, `uri`, and `binding` tags as appropriate. Never use `gin.H`.
- Prefer a generic helper when identical behavior applies to multiple types; for example, use `pkg/types.Value[T]` for pointer value defaults.
- UI DTOs use project enums directly for statuses, transaction types and transfer kinds in both requests and responses. UI filters preserve the exact supplied enum instead of converting through third-party enums or broadening to equivalent states. Only OpenAPI and webhook protocol DTOs convert to channel enums. Declare each DTO field with its enum type, not an intermediate `string`. Frontend business-page components are shared by module, with typed API adapters and explicit capabilities for channel differences; keep webhook event choices channel-specific and load them from the backend.
- Use GORM Gen query objects for data access. Do not write literal SQL predicates such as `Where("field = ?")`.
- If a flow allows a resource to be absent, use a separate one-query `Exist` repository method before `Find`. Do not convert or inspect `RecordNotFound` to implement optional-resource behavior.
- In biz, log an unexpected repository error exactly once at its first handling point with direct `zap.S().Errorw`, then return a Kratos error. Do not hide logging behind a private error helper. Expected `Exist=false` results do not need error logs.
- Define all Kratos business errors centrally in the channel's independent `channel/<channel>/errors` package, not in `biz`. Biz, service, HTTP and ID-conversion helpers import the named errors directly; do not retain aliases in biz or make the errors package depend on those layers. Preserve existing status codes, reasons and messages when relocating definitions, and never construct business errors with literal reasons or messages inline.
- Apart from `context.Context`, methods with multiple inputs accept a request struct.
- All optional single-value parameters and request fields use pointer types at the service, usecase, and repository boundaries. `nil` means omitted; a non-nil pointer means explicitly supplied, including a zero value, which must be validated according to the field's rules. Do not use `!= 0`, `!= ""`, `false`, or any other zero-value sentinel to infer presence. For example, a UI list's optional account selector is `AccountID *model.ID`: only `nil` omits that selection; a supplied invalid ID must be rejected rather than broadening the query. Biz maps it to the repository's `AccountIDs` slice. Required account/resource IDs remain required and validated; multi-value query filters follow the slice rule below.
- Use a dedicated biz `Transaction` interface with `InTx(ctx, func(ctx context.Context) error)` for write flows requiring more than one database operation. Keep aggregate repos as small separate interfaces. Data repositories resolve query objects through `repo.DB(ctx)` and must use the transaction stored in the context.
- Every list query needs explicit ordering. Default to primary `ID DESC` unless the channel contract says otherwise.
- Retrofit existing repository list/count equality filters, and design new ones, as multi-value slices (`AccountIDs`, `IDs`, `Statuses`, etc.). Use `IN` guarded by `len(values) != 0`; empty slices omit only that filter. Never drop supplied zero/empty elements. Slices are the collection exception to the optional-pointer rule; non-collection optional filters (time bounds and substring searches) remain pointers. Keep required resource, ownership, and locking inputs required. HTTP fields retain the product's single-selection contract; biz assembles repository slices, without exposing both singular and plural filters.
- Prefer GORM Gen `Preload` for existing read-only associations used only to populate response data (including `Account` for `account_name`), instead of joins with hand-written association-column aliases. A repository operation can include ORM-managed preloads; it must not manually query related rows in a loop. Always retain the base query's channel and ownership filters.
- Ignore authentication/signature validation unless a channel-specific requirement explicitly asks for it.
- Preserve unused SDK fields only in service DTOs, label them `Invalid:`, and do not persist or implement their behavior.
- A service DTO uses `time.Time` or `*time.Time` when the downstream JSON time is RFC3339, letting the HTTP codec perform the standard conversion. For non-RFC3339 timestamps, use the time-backed types in `pkg/types/time`: `DateTime` for Paynda's `2006-01-02 15:04:05` and `ISODateTime` for PhotonPay's `2006-01-02T15:04:05`. Do not represent timestamps as strings or format them manually in service mappings. Paynda query timestamps use `*DateTime`, whose `UnmarshalParam` handles format validation and UTC parsing; do not repeat format/timezone tags on those fields. Omitted optional parameters remain nil; explicitly supplied empty or malformed timestamps must fail binding. `DateTime` JSON decoding retains its existing local-time semantics. Other query timestamps use `time.Time` pointers for optional fields with explicit binding format/timezone tags. Partial dates such as card expiry remain channel-formatted strings.

### GORM Model Schema

- Every persisted scalar field in `model` has an explicit GORM `column` and PostgreSQL `type` tag. Associations have no physical column tag; declare their `foreignKey` and `references` explicitly instead.
- Strings and string-backed enums use `type:varchar;not null;default:''`. Numeric IDs and counters use their explicit integer type with `not null;default:0`; decimal values use `type:numeric;not null;default:0`; booleans use `type:boolean;not null;default:false`; JSON values use `type:jsonb;not null;default:'{}'`.
- `time.Time` and `*time.Time` model fields use `type:timestamptz`. Required values are `not null`; optional pointer values use `default:null`.
- Model associations used by GORM Gen `Preload` are read-only: add `gorm:"...;->"` so aggregate saves never persist preloaded related objects.
- A card transaction represents one concrete transaction stage. Its `CreatedAt` is that stage's event time; do not add `OccurredAt` or `SettledAt` to `CardTransaction`. For a transaction DTO's authorization timestamp, preload its `Authorization` and use `Authorization.CreatedAt`, never the transaction's creation time.
- This mock may reset its local business tables when a model schema changes. Do not add compatibility field mappings or retain deprecated columns solely to preserve local mock data unless the user explicitly requires a migration.

### Naming

- PingPong terminology boundary: `budget` / 预算组 belongs only to its OpenAPI contract (HTTP paths, SDK request/response DTOs and their service-boundary mapping). Everywhere inside usecases, repositories, generic/channel-internal enums, local variables, logs, filenames, UI DTOs, UI routes and browser labels use `VirtualAccount` / `virtualAccount` / `virtual_account` / 虚拟账户. Parse OpenAPI `budget_id` and `target_budget_id` into `VirtualAccountID` and `TargetVirtualAccountID` before calling a usecase; map them back only when producing OpenAPI DTOs. UI uses `/virtual-accounts` and `virtual_account_id`, never `budgets` or `budget_id`. Do not alter the external OpenAPI contract or persisted values merely to rename internal identifiers.

- Service receivers may use `s`, and injected usecases may use `uc`; short names should retain an obvious role within their scope.
- Repository dependencies retain a descriptive resource name and the `Repo` suffix, such as `accountRepo`, `cardProductRepo`, or `cardTransactionRepo`. Do not shorten them to `account`, `accounts`, `cards`, or `transactions`, which can be confused with domain data.
- Conversion and parsing functions name the action and the data involved: use `ParseAccountAndResourceIDs`, `toAccountData`, or directional `To...` / `From...` names, not noun-only helpers such as `IDs()` or `accountData()`. Keep channel resource ID encoding/decoding in the existing `pkg/idconv` helpers.
- Helpers that resolve defaults, look up data, or calculate values should likewise expose that action, for example `resolvePagination`, `resolveAccountID`, and `CalculateRemainingAuthorization`. Pure model getters belong on the model rather than in service helpers.

### Code Layout

1. Do not compress code merely to reduce line count.
2. A struct literal with multiple fields uses a multi-line layout, with one field per line.
3. Split a function call with many arguments, or one that would become long, across multiple lines.
4. Split a multi-variable assignment across multiple lines when its right side contains multiple fields or expressions.
5. Do not put multiple business operations on one line.
6. Passing `gofmt` is not a reason to retain a compressed one-line layout.
7. Prefer readability over line count.
8. Do not proactively compress existing multi-line code into one line while making a change.
9. New code follows these rules even when a compressed line would be 120 characters or fewer.
10. Before submitting Go changes, review hand-written code matched by `\{.*?,.*?,`. Treat each match as a readability warning: expand obvious multi-field literals, multi-argument calls, and combined business operations; exclude generated code and do not mechanically rewrite a legitimate single-field nested literal.
11. Before submitting repository queries, review hand-written code matched by `Where.*?,.*?.(Find|Count|Create)\(\)`. Split a `Where` call with multiple conditions and its terminal `Find`, `Count`, or `Create` call across lines; exclude generated GORM Gen code.

- Card issuance must explicitly specify a channel product (the contract's product ID or BIN). UI card-creation requests require `card_product_id`; OpenAPI retains its required protocol field. Do not persist a default-product flag or select a seeded/first/default product when input is omitted. All implemented channels expose the shared product-list management page.
- `CardProduct` is channel-level configuration with no `AccountID`. Scope product lookups by `Channel` (and `ID` or `Prefix`), enforce uniqueness on `(channel, prefix)`, and share its issuing sequence across accounts. Creating an account must not create or copy products; cards still belong to accounts and may reference only products of the same channel.
