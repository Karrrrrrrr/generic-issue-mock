# Generic Mock Constraints

Read [AI_GUIDELINES.md](AI_GUIDELINES.md) before changing this repository.

- This service simulates channels for downstream systems. Do not use downstream-perspective names such as `ThirdPartyID` in generic models. Use the auto-incrementing `int64` primary key `ID` for relations and transactions. Derive external channel resource IDs directly from that key; do not persist `display_id` or add a second resource token.
- Channel services must format outgoing mock-owned resource IDs and parse incoming ones with the channel's ID conversion helpers in `channel/<channel>/pkg/idconv`, exposed as public functions with directional `To...` / `From...` names before calling a usecase. The helpers must be reversible and validate the downstream-required format. A downstream string ID uses decimal `int64` formatting and parsing; a downstream numeric ID uses the `int64` value; a UUID or other required representation uses a deterministic reversible encoder. Do not introduce prefixes, offsets, hashes, or other encodings when the downstream contract does not require them.
- Implemented channel ID formats: `slash` uses canonical UUID strings with the internal ID encoded in the final 8 bytes; `photonpay` uses decimal strings; `paynda` uses decimal strings for OpenAPI/UI IDs and numeric `int64` values for `xm-event` webhook fields declared as `int64` by Marxo. Paynda string webhook IDs remain decimal strings. See `AI_GUIDELINES.md` for the field-level table and sources of truth.
- Generic models are shared by all channels. Persist only channel-neutral concepts required by an implemented channel. Leave unused third-party API fields in the channel service DTO, tagged with an `Invalid:` comment.
- `Account` is a channel account domain and retains `Channel`; it is distinct from `VirtualAccount`. Every persisted business table except `Account` and channel-level `CardProduct` must include `AccountID` and `Channel`, and every repository operation must scope by that pair. Child records inherit the pair from their owning aggregate. Unique indexes for account-owned data include `account_id` and `channel`; never encode either into an external resource ID.
- Use `channel/<channel>/{service,biz,data,http}`. Service converts typed HTTP DTOs; biz owns business behavior and repo interfaces; data uses GORM Gen.
- Repositories perform one database operation per method. Use `samber/do` for dependency injection, typed bind/tag DTOs rather than `gin.H`, and no raw GORM `Where("...")` predicates.
- Put every channel route under `/<channel>/...`; do not validate tokens unless explicitly required.
- Service methods return their channel DTO directly. The channel HTTP adapter owns the protocol success envelope; service translates business errors to channel error codes with Kratos errors.
- When a business flow permits a resource to be absent, call an explicit one-query `Exist` repository method before `Find`; never infer absence by handling `RecordNotFound` or a sentinel not-found error.
- Log unexpected repository errors once in biz at their first handling point with direct `zap.S().Errorw` calls. Do not wrap logging in a private error helper, log expected absence, or repeat a log while propagating the same error.
- Define all Kratos business errors centrally in the channel biz error definitions. Use those named errors in usecases; do not construct business errors with literal reasons or messages inline.
- Except for `context.Context`, methods with more than one argument use a request struct.
- Repository request structs must be defined separately in biz for the specific repository operation, with names that identify the resource and operation. Do not reuse service/usecase requests or ambiguous catch-all types such as `ManagementScope`, `ResourceRequest`, or a channel-wide `ListRequest`. A dedicated request may embed a clearly defined common field struct, but each operation retains its own request type; a type alias is not a substitute.
- Keep biz repository interfaces in dedicated repository-definition files, never in usecase files. Put repository parameter structs at the top of the same file (after package/imports), before the interfaces that use them. Keep usecase logic and usecase-owned requests in usecase files; do not create a separate file for each parameter struct.
- Organize files by business domain, not by putting an entire channel in one `usecase.go` and one `repository.go`. Use domain-specific files such as `account_repository.go`, `account_ui.go`, and `account_openapi.go`; keep UI/OpenAPI implementations separate. A small constructor/composition file may wire dependencies, but must not accumulate business methods. Repository operation requests remain at the top of their domain's repository file.
- All optional single-value parameters and request fields must use pointer types. `nil` means omitted; a non-nil pointer means explicitly supplied and must be validated as such. Never use `!= 0`, `!= ""`, or other zero-value checks to decide whether an optional parameter was supplied. Required fields remain required; invalid zero values must not silently disable account or resource filtering. Multi-value query filters follow the slice rule below.
- Repository list/count filters that support multiple values use slices (for example `AccountIDs`, `IDs`, and `Statuses`) and `IN`; add the condition only when `len(values) != 0`. Empty slices omit that filter, and supplied zero/empty elements must never be discarded to broaden the query. This rule applies to existing and new repositories. Optional single-value filters that cannot use `IN` (time bounds, substring searches) use pointers. Keep required resource/ownership/locking parameters required. HTTP single-selection fields remain singular; biz maps them to repository slices. Do not expose both singular and plural versions of the same filter.
- Load existing model associations with GORM Gen `Preload` when they are needed only for response fields such as account names; do not hand-write joins and aliased association projections for that purpose. One repository operation may include its ORM-managed preloads; do not manually query associations in a loop.
- Register layer constructors directly as `samber/do` providers. Do not manually resolve and thread dependencies through registration closures.
- Define `InTx(ctx, func(ctx context.Context) error)` only on a dedicated biz `Transaction` interface. Keep aggregate repos separate; their data implementations resolve GORM Gen queries through `repo.DB(ctx)` so every operation uses the transaction carried by the context.
- Every list query must include an explicit order. Unless a channel requirement says otherwise, order by primary `ID DESC`.
- Run the generator after model changes, then `gofmt` and `go build ./...` with the configured Go cache paths. Do not run unit tests unless asked.
- Treat `../workspace/ptm/marxo/pkg/dealer/<channel>` as the source of truth for an implemented channel OpenAPI. Match its HTTP method, path, bind field names, response envelope, and response DTO fields; do not substitute a UI contract for an OpenAPI contract.
- Before adding or changing an OpenAPI endpoint, inspect both the SDK request/response DTOs and its actual call sites in Marxo. Implement every endpoint used by those call sites. SDK-only fields that have no channel-neutral persistence need stay in the channel service DTO with an `Invalid:` comment.
- Keep browser UI services/usecases separate from OpenAPI services/usecases. They may share well-factored repositories, but never call each other.
- Simulation amounts must be positive. Simulated authorization and clearing must not reject insufficient wallet balances or exhausted authorization amounts; allow over-clearing and continued clearing with negative wallet/remaining balances. Preserve signed remaining amounts instead of clamping them to zero. These exceptions do not relax normal wallet-transfer checks.
- Clearing and reversal must reference an existing authorization (`AuthorizationID != 0`) in the same account/channel and card. Refunds may be independent (`AuthorizationID = 0`) or reference an existing authorization; do not require a prior clearing transaction. Optional authorization request fields use pointers and channel ID helpers; persist zero for an independent refund. Do not infer opposite accounting directions between authorization and clearing.
- Account-associated UI responses must include `account_name` alongside `account_id` in the original endpoint DTO. Resolve names on the backend; never make the frontend issue an extra account-list request merely to display names. Account-selection forms may still fetch account options.
- Service-facing enum fields must use the channel enum defined under `channel/<channel>/enums`, or a genuinely common external value type such as ISO currency. Declare the DTO field with that enum type directly; do not use `string` as an intermediate enum representation. Never expose a generic enum by casting it to `string`; provide conversion functions at the service boundary.
- Model time fields are `time.Time` or `*time.Time`. A service DTO uses `time.Time` or `*time.Time` directly when the downstream JSON format is RFC3339, including OpenAPI DTOs; the HTTP codec performs the conversion. Use a `string` field only when the third-party contract explicitly requires a non-RFC3339 layout or a non-time textual value, and perform that conversion at the service boundary. UI DTOs return time values unformatted.
- Channel OpenAPI error codes must preserve downstream control-flow semantics. In particular, PhotonPay's absent request result must be encoded as `VCC1039`, allowing Marxo to issue the operation after its idempotency probe.

- `CardProduct` is channel-level configuration with no `AccountID`. Scope product lookups by `Channel` (and `ID` or `Prefix`), enforce uniqueness on `(channel, prefix)`, and share its issuing sequence across accounts. Creating an account must not create or copy products; cards still belong to accounts and may reference only products of the same channel.
